# protoST — Status

**This document is the living delta between [`docs/LANGUAGE.md`](LANGUAGE.md)
(the *ideal* — what protoST is specified to be) and the implementation (the
*reality* — what the current build actually does).**

`LANGUAGE.md` describes the language as designed. This file records, item by
item, where the implementation has not caught up, where it deviates *on
purpose*, and what is genuinely broken. It is a tracker, not a reference.

**It must be updated with every change that opens or closes an item.** When a
bug is fixed, move it to *Closed items* with the fixing commit SHA. When a
"not yet implemented" feature lands, move it to *Implemented* and tick the
relevant checklist line. When a new divergence is discovered, give it a fresh
stable id and file it in the right bucket.

## Implemented

What works today, by area. Phase/track tags (`f1-complete` … `track11-complete`)
are noted where useful.

### Lexer / parser
- [x] Comments, identifiers, keyword tokens
- [x] A leading `#!` interpreter line is skipped, so a script with
      `#!/usr/bin/env protost` runs as a command; later line numbers are
      unchanged *(0.6.6)*
- [x] Integer literals, float literals, character literals, string literals,
      symbol literals *(f1-complete)*
- [x] Flat array-literal syntax `#( … )`
- [x] Dynamic-array syntax `{ … }`
- [x] Operators, the `>>` method marker, cascades `;`
- [x] Class declarations (`subclass:` / `instanceVariableNames:`)
- [x] Method definitions (unary / binary / keyword selector patterns)
- [x] **Call-form method declarations** `Class >> name(p, k = default)`
      and **call-form sends** `recv name(p, k = v)` — protoCore convention,
      coexists with Smalltalk forms. Known restriction: a class cannot
      host both `>> bar` (unary) and `>> bar(...)` (call) on the same
      name. Actor receivers reject call-form sends in v1.
      *(closed: 2026-06-13)*
- [x] Message-precedence parsing (unary > binary > keyword)
- [x] **Chained assignment** `a := b := 0` *(closed: C1)*

### Object model
- [x] Everything is an object; prototype-based model
- [x] Defining a class; creating instances via `new`
- [x] Instance variables; a run of assignments to them is published as one
      version of the object, so another thread sees all of it or none of it
      (LANGUAGE.md 4.5; `tests/unit/test_instvar_groups.cpp`). Compiled to
      `IVAR_GROUP` ... `IVAR_GROUP_END` and published with protoCore's
      `setAttributes`, hence the protoCore 2.11.0 floor *(`207bdeb`, after
      0.5.0; `PROTOST_IVAR_GROUPS=off` disables it)*
- [x] `self` / `super` sends
- [x] Class-side methods on a metaclass, isolated from instances and instances' methods isolated from the class (D5, D52), with one selector definable on both sides of a class (KNOWN_ISSUES K14, resolved); class variables and class-instance variables
- [x] `printString`
- [x] **Extensible classes from modules** — `subclass:` is a runtime message
      on any class object, so an imported module class can be subclassed in
      the importing program, methods overridden, and `super` used in an
      override to reuse the module's implementation *(Track 3, T3-a)*
- [x] **Multiple inheritance / mixins** — a class may be defined with several
      superclasses / mixins via the `uses:` clause
      (`Object subclass: #Foo uses: { MixinA. MixinB }`, also
      `subclass:instanceVariableNames:uses:` and the expression-receiver
      message form). Method/attribute lookup and `super` walk the parents
      depth-first, left-to-right — the primary superclass subtree first, then
      each mixin subtree in listed order; the diamond case resolves to the
      first in that order. Mixin instance variables work. *(Track 3, T3-b)*
- [x] **On-the-fly behaviour composition** — `aClass addBehavior: aMixin`
      (lower-level alias `addParent:`) composes a behaviour into a class at
      runtime with no recompilation. The class object and every instance
      created *after* the call respond to the mixin's methods. *(Track 3,
      T3-c)* — see D21 for the documented "future instances only" limitation.

### Blocks / closures
- [x] Block syntax, 0–4 argument blocks
- [x] Closures with variable capture *(f1-complete)*
- [x] `whileTrue:`, `to:do:`, `to:by:do:`
- [x] Compile-time inlining of `ifTrue:`, `ifFalse:`, `ifTrue:ifFalse:`,
      `ifFalse:ifTrue:`, `and:`, `or:` (0.10.0), `whileTrue:`,
      `whileFalse:`, `to:do:`, and `ifNil:` / `ifNotNil:` / `ifNil:ifNotNil:` /
      `ifNotNil:ifNil:` (0.10.0, identity with nil as in Pharo) with literal
      blocks, and `==` (0.10.0, never looked up, as in Pharo); a non-Boolean receiver
      of an inlined conditional gets the real send, with closures for the
      block literals (0.10.0): its own method, or `doesNotUnderstand:` with
      the whole Message. A closure it keeps and evaluates after the send
      returned signals an Error when it uses the method's variables
      (docs/VM.md 1.4). Pharo 10+ signals `NonBooleanReceiver` here instead;
      Pharo 9 re-sent the expression, as protoST does. A loop condition
      that is not a Boolean signals the resumable `NonBooleanReceiver` in
      every loop form, inlined or sent; the resumed value is true unless it
      is false, as in Pharo (0.10.0)

### Actors / futures
- [x] Promoting an object to an actor; asynchronous message forwarding
- [x] `Future`: `wait`, `thenDo:`, `catch:`, `resolve:`, `rejectWith:`
- [x] **`Future new`** yields a usable first-class promise *(closed: C3)*
- [x] Cooperative suspension; parallel scheduler
- [x] **Lock-free actor mailbox + Future** — no per-actor or per-future mutex.
      The mailbox is a protoCore `ProtoMPSCQueue` (Track S): a send is one
      lock-free O(1) `push`, and a turn drains a whole batch with `takeAll`.
      The Future state machine and the scheduler run on protoCore's atomic
      attribute compare-and-swap (`setAttributeIfEqual`).
      The message path (send, mailbox, Future, ready queues) takes no lock.
      Runtime bookkeeping kept outside protoCore's object model does use
      mutexes: among others the module-provider registry, the compiler's
      class registry, the unobserved-rejection list, the DAP/debugger I/O
      and, since 0.5.0, the I/O descriptor table and the growth of the
      worker pool.
- [x] **`Atom`** — a shared mutable cell with optimistic-concurrency CAS:
      `Atom on:`, `value`, `value:ifCurrent:` (the raw compare-and-swap) and
      `swap:` (the read-modify-CAS retry loop). The agent/atom pair, atom
      side. Plus `Object>>setInstVar:from:to:` — the raw CAS exposed on any
      instance variable, for callers driving their own validate-and-retry.
- [x] **Actor priority bands (2026-06-15)** — three strict-priority queues
      backing the existing lock-free scheduler: `asActor` is Medium (the
      default, backward compatible), `asHighPriorityActor` lands in High,
      `asLowPriorityActor` in Low. Workers drain High → Medium → Low.
      Priority affects WHICH actor a worker picks up next; within-actor
      mailbox order is unchanged and the single-method invariant holds in
      every band. See `examples/actors/05_priority_bands.st`.

### Modules
- [x] File-to-module mapping; `Import from:`
- [x] protoCore UMD provider registration
- [x] **`Import from:` on every thread; each module's top level runs once** —
      imports work inside actor methods (and on any other thread running
      protoST code); concurrent importers of a module that is still loading
      wait for that load and receive the same module object; an import cycle
      raises `cyclic module import`. *(closed: S6)*
- [x] **Cross-language UMD interop, consumer side** — protoST `Import`s a
      module published by *any* registered `proto::ModuleProvider`, not just
      its own `provider:st`. `STRuntime::addModuleProviderToChain` wires a
      foreign provider's spec into the resolution chain; foreign objects
      dispatch protoST messages, carry through collections and blocks, and
      foreign immediates/strings need no conversion. Strategy:
      [`docs/INTEROP.md`](INTEROP.md). *(Track 5, T5-a)*

### Packaging
- [x] **CPack installers** — `cmake --build` followed by `cpack` produces
      native packages: `.deb` / `.rpm` / `.tar.gz` on Linux, a `.dmg` on
      macOS, an NSIS installer + `.zip` on Windows. The `protost` binary
      installs to `<prefix>/bin`; the stdlib `.st` modules to
      `<prefix>/share/protoST/lib` (the discovery in `STRuntime.cpp` probes an
      install-relative `<exe>/../share/protoST/lib`, so an installed binary
      resolves `Import from: …` with no `PROTOST_LIB`). The Debian package
      depends on `protocore` and the RPM `Requires: protoCore`. `cpack -G DEB`
      and `-G TGZ` verified on Linux; the Windows ZIP, which carries
      protoCore's DLL, the OpenSSL DLLs with OpenSSL's licence and the MSVC
      runtime next to `protost.exe`, is built and run from a clean directory
      by the cross-platform CI job (NSIS is built when `makensis` is found);
      the macOS `.dmg` has not been built. *(Track 10)*

### Documentation
- [x] **The dual-audience tutorial** — [`docs/TUTORIAL.md`](TUTORIAL.md) plus
      15 chapters under `docs/tutorial/` (chapter 15, input and output, added
      in 0.5.0). Teaches protoST from the ground up
      for Python / JavaScript developers (with a constant Python/JS bridge) and
      catalogues every departure from Smalltalk-80 for Smalltalk programmers
      (Chapter 14). Every non-trivial code snippet was executed against the
      `protost` build. *(Track 8)*
- [x] **The comprehensive example set** — 42 complete, idiomatic, runnable
      protoST programs under `examples/`, grouped by theme (`basics/`,
      `blocks/`, `collections/`, `exceptions/`, `nonlocal/`, `actors/`,
      `stdlib/`, `modules/`, `programs/`). They span focused single-feature
      illustrations through genuine end-to-end programs — a recursive-descent

      `examples/README.md` indexes the set. *(Track 9)*

### Benchmarks
- [x] **Performance benchmark suite** — `benchmarks/` carries two benchmark
      families and a harness. `benchmarks/comparable/*.st` is the protoPython
      core benchmark suite translated to idiomatic protoST (same algorithm,
      same N), so `benchmarks/run_benchmarks.py` can place protoST, CPython
      and (when a built `protopy` is found) protoPython side by side.
      `benchmarks/actors/*.st` are actor-model benchmarks with no Python
      counterpart — parallel speedup, cooperative-yield scaling (1000 actors
      on K=2 worker threads) and mailbox throughput. The harness does warmup +
      timed runs, reports the median and a geometric mean, and writes a dated
      report; `benchmarks/reports/2026-05-21-baseline.md` is the first one and
      `README.md` carries the headline numbers. *(Track 11)*

### Standard library
- [x] `lib/` infrastructure + the `Stream` module *(track4, T4-a)*
- [x] Mathematical protocol — `sqrt`, trig (`sin`/`cos`/`tan` + inverses),
      `ln`/`exp`/`log`/`log:`, rounding (`floor`/`ceiling`/`rounded`/
      `truncated`), `sign`/`squared`/`reciprocal`/`isZero`/`min:`/`max:`/
      `between:and:`/`asFloat`/`asInteger`/`even`/`odd`/`gcd:`/`lcm:`,
      exact `raisedTo:` and `factorial` (LargeInteger-safe), and class-side
      `Float` constants (`pi`/`e`/`infinity`/`nan`). Bootstrapped C++
      primitives on `Number` — always available, not a loadable module
      *(track4, T4-b)*
- [x] `lib/random.st` — the `Random` module: a seedable, deterministic
      pseudo-random generator (`seed:`, `new`, `next`, `nextInt:`,
      `between:and:`, `next:`). Pure protoST, a 32-bit LCG; no new
      primitives. Integer draws scale the state's high bits into the range
      (0.10.0; until then the low bits, which alternate) *(track4, T4-c)*
- [x] `lib/json.st` — the `JSON` module: `JSON parse:` (a JSON document →
      `Dictionary` / `Array` / `String` / number / `Boolean` / `nil`,
      recursive to any depth) and `JSON stringify:` (the inverse, with JSON
      string escaping). A hand-written recursive-descent scanner, pure
      protoST. Required two enabling additions, since the `String` protocol
      previously exposed no character access: minimal `String` accessors
      `at:` / `asInteger` and `Number>>asCharacter` (UTF-8-aware codepoint
      conversion), and registering `String` / `Boolean` as globals so the
      module can extend them with double-dispatch methods *(track4, T4-d)*
- [x] `lib/time.st` — the `Time` module: wall-clock access with a small
      timestamp / duration object model. `Time now` answers a `Timestamp`
      for the current instant; `Time millisecondsToRun:` benchmarks a block.
      `Timestamp` wraps epoch milliseconds (`asMilliseconds` / `asSeconds`,
      comparison, `Timestamp - Timestamp → Duration`,
      `Timestamp + Duration → Timestamp`); `Duration` wraps a millisecond
      span (`seconds:` / `milliseconds:` / `minutes:` constructors,
      arithmetic, comparison). Backed by two C++ clock primitives
      (`__currentMillis` from `system_clock`, `__monotonicMillis` from
      `steady_clock`) bootstrapped onto Object; no timezones, no calendar
      *(track4, T4-e)*
- [x] `lib/kernel/io.st` — input and output in the kernel, no import
      *(0.5.0)*: `Stdio stdin` / `stdout` / `stderr` and `IOStream`
      (`nextLine`, `upToEnd`, `linesDo:`, `nextPutAll:`, `print:`, `<<`,
      `flush`, `timeout:`, `close`); files and directories with Pharo's names
      (`'p' asFileReference`, `File named:`, `FileSystem temp` / `home` /
      `workingDirectory`, `/`, `contents` / `contents:`, `appendContents:`,
      `lines`, `binaryContents`, `readStreamDo:` / `writeStreamDo:`,
      `children`, `copyTo:`, `moveTo:`, `delete`, `deleteAll`, …); the
      program's arguments and environment on `Smalltalk` (`arguments`,
      `programPath`, `getenv:`, `setenv:to:`, `environment`, `exit:`, `pid`,
      `workingDirectory`, `changeDirectory:`); other programs through
      `OSProcess` (`run:arguments:input:`, `shell:`, `command:`, `spawn:`,
      `waitFor:`, `kill:`). Classed errors: `FileSystemError`,
      `FileDoesNotExist`, `FileAlreadyExists`, `NetworkError`,
      `ConnectionRefused`, `ConnectionTimedOut`, `NameLookupFailure`,
      `OSProcessError`. The primitives are C++ (`src/primitives/io_prims.cpp`);
      every blocking call leaves the GC quorum (a line `nextLine` finds already

      makes the pool add a worker when fewer than the configured number would
      remain free (at most 256 threads; added workers stay until exit). Tests:
      `conformance/14-io/files_*`, `os_*`, `cli_io`. Binary data was an Array of
      integers 0–255 up to 0.8.1; since 0.9.0 it is a `ByteArray` (the next
      entries); `next` / `next:` read whole UTF-8 characters, `nextByteCount:` counts bytes

## Intentional deviations

protoST is **not** standard Smalltalk here, on purpose. These are design
decisions, not defects; they stay, documented with their rationale.

| Id | Deviation | Rationale |
|----|-----------|-----------|
| D53 | **A non-Boolean receiver of an inlined value conditional gets the real send (Pharo 9), while a non-Boolean loop condition signals `NonBooleanReceiver` (Pharo 10+).** `x ifTrue: [...]`, `ifFalse:`, `ifTrue:ifFalse:`, `ifFalse:ifTrue:`, `and:` and `or:` with literal blocks are compiled inline; when `x` is not a Boolean, an out-of-line path sends the selector to `x` with closures over copies of the literal blocks (compiled without inlining). The frame variables the arms use travel in a box and are copied back when the send returns. A loop condition that is not a Boolean signals the resumable `NonBooleanReceiver` (resumption `~~ false` is the truth), as `ProtoObject>>mustBeBooleanIn:` does in Pharo 10-15. Two consequences: a block literal of such a conditional that the receiver keeps and evaluates after the send returned signals an `Error` (Pharo 9's de-optimised blocks keep working); and if the receiver hands such a block to another thread that runs it while the send returns, the copy-back races the other thread's writes: a write after the copy-back is lost and a read sees the old value (a real closure's write would land). *(Decision [agent, pending review], 2026-11-11; protoBaseST review M2, round 2.)* | The two cases differ: in a conditional the non-Boolean is the receiver of a message the source wrote, so it has a method that can answer; a loop condition is a block's value that no message has as receiver. Current Pharo uses one rule (`NonBooleanReceiver`) for both; Pharo 9 re-ran the conditional without inlining (`mustBeBooleanDeOptimizeIn:`). The real send keeps user `and:` / `ifTrue:` DSLs and forwarding proxies working (protoBaseST query builders, `q1 and: [q2]`, are the plausible users) and matches protoST before 0.10.0, where `and:` / `or:` were sent. Cost: opcodes 46-49, about 400 lines in the compiler and engine, about 7 M instructions of startup (the cold copies of the kernel), and the kept-block rule. Reversal: replace the out-of-line path with the loop rule (signal `NonBooleanReceiver`, resumption `~~ false` as the condition), which deletes the box machinery and the startup cost. |
| D52 | **A class is not an instance of itself: class-side methods live on a metaclass, and a send to a class looks up the metaclass chain only.** Every class has a metaclass (`Foo class`), a separate object that holds `Foo`'s class-side methods; its parent is the superclass's metaclass, `Object class`'s parent is `Class`, `Class` and `Metaclass` descend from `Behavior`, and `Behavior` from `Object`, the chain of Pharo without `ClassDescription`. A send to a class starts at its metaclass (`Foo class` -> ... -> `Object class` -> `Class` -> `Behavior` -> `Object`) and never reaches `Foo`'s instance-side methods; a send to an instance never reaches a metaclass. Every send path (SEND, `super`, the call form, `perform:`, foreign and actor sends, `doesNotUnderstand:`, `respondsTo:`) is one lookup from that start. The class protocol (`new`, `basicNew`, `subclass:`..., `name`, `selectors`, `canUnderstand:`, `superclass`, `instVarNames`, `inheritsFrom:`...) is on `Behavior`; the built-in constructors are on their classes' metaclasses. `Foo class class == Metaclass`, `Foo class superclass == Super class`, `Object class superclass == Class`. `canUnderstand:` describes the receiver's instances (`Array canUnderstand: #at:put:` is true, `Array class canUnderstand: #at:put:` false). The metaclass protocol is Pharo's: `isMeta`, `soleInstance` / `instanceClass`, `instanceVariableNames:` answering the receiver, `copy` of a class giving the copy a metaclass of its own; a metaclass has one instance, so `Metaclass new` and `Foo class new` signal an `Error`, and `Behavior new` / `Class new` signal one too (deviation: Pharo's `Class new` makes an anonymous class; protoST has no anonymous classes). `isKindOf:` and `inheritsFrom:` count `uses:` / `addBehavior:` mixins, the ancestor set lookup and `on:do:` use (LANGUAGE.md §4.11). Deviation: `lookupSelector:` answers the behavior (class or metaclass) that holds the method, or nil, where Pharo answers the CompiledMethod; protoST has no method objects. This supersedes the half of D5 that let a class answer its own instance-side methods. *(Decision [controller, recorded as review ruling Q19], 2026-11-11.)* | D5 left `Foo >> m` reachable as `Foo m` because the built-in prototypes doubled as class object and instance-behaviour holder and the separate metamodel was judged too large for that slice. The leak had costs the maintainer directive ("no conceptual or technical debt", "follow the source language by default") does not accept: one selector could not name a method on each side without a second storage key and a second lookup per send (the first K14 fix), `Foo = Foo` ran an instance-side `=` on the class (a class with a value `=` could not be a `Set` key, and the kernel carried 37 `isClassObject` guards against such calls), and every constructor had to be bound twice so that a kernel class-side method would not hide it. With a metaclass each side is an attribute of its own object, the lookup is protoCore's ordinary one, and the guards are gone. Consequences: code that sent an instance method to a class (`Random seed:` style workarounds, class objects used as mutable globals through an instance-side setter, `anInstance new`) now gets `doesNotUnderstand` and must define the method on the class side; `Exception class >> signal` / `signal:` remain, building an instance. protoBaseST's lib relies on the leak in places (see the K14 report). Cost of reversing: give `methodHolder` its old answer and restore the 37 guards. |
| D51 | **A float literal is the nearest `Float`, subnormals and underflow included; only overflow is refused.** The lexer reads a float literal as the correctly rounded IEEE 754 double (round to nearest, ties to even). A value below the smallest normal `Float` is the nearest subnormal (`5e-324` is a literal), one below half of `5e-324` is `0.0` or `-0.0` (`1e-400` is `0.0`), and one whose nearest `Float` is infinite (`1.0e309`) is the compile error *float literal out of range*. Up to 0.9.0 every literal whose value is subnormal or underflows was that error too, and the smallest subnormal could not be written (KNOWN_ISSUES K16). `String >> asNumber` was already correctly rounded and is unchanged: it reads `'1e400'` as `Float infinity`, as Python's `float()`. Both read the text with `std::from_chars`, which ignores the C locale (until fix round 1 they used `strtod`, which a host setting `LC_NUMERIC` to a comma-decimal locale would have changed). An integer mantissa with a negative exponent (`1e-5`) is a `Float`, where Pharo answers the `Fraction` `1/100000`; with a positive exponent (`1e309`, `2e3`) it is an `Integer`, as in Pharo. The `Float` reading of `1e-5` is a recorded deviation, kept because protoST has no fraction literal and the code that writes `1e-5` (protoBaseST included) means a `Float`. *(Decision [agent, pending review], 2026-11-11.)* | IEEE 754 rounds an underflowing value to the nearest representable one, and Pharo and Python read such literals that way, so `printString` of every finite `Float` can be read back (it prints `5.0e-324`). Underflow loses at most half of `5e-324`, the representation's own resolution; overflow has no finite value at all, and a literal that silently became infinity would hide a typo or a missing scale, while `Float infinity` writes that value explicitly. Pharo and Python make it infinity; protoST keeps the error it already had. Cost of reversing: one line in `Lexer::lexNumber` and `02-lexical/float-literal-overflow-is-error.st`. |
| D50 | **Calendar values are protoST's own classes. They count microseconds; `Date`, `Time` and `Duration` keep their kernel meaning. There is no IANA database: a named zone keeps its key, and a wall clock in it is refused with `TimeZoneUnavailable`.** `lib/calendar.st` (`Import from: 'calendar'`) adds `CalendarDate`, `TimeOfDay`, `DateTime`, `TimeSpan`, `ZoneOffset`, `ZoneName` and `TimeZoneUnavailable` (an `Error`), with Python's `datetime` model, not Pharo's `DateAndTime` / `Timespan` / `TimeZone`. A `DateTime` in a `ZoneName` exists only in the instant form (`utcFields:zoneName:`, fields = UTC instant, fold 0); building one from a wall clock, and its `wallClock`, `date` and `time`, signal `TimeZoneUnavailable`. Two instant-form values compare by instant, also in the same zone, where Python compares wall clocks ignoring `fold`: the two disagree only inside a repeated wall-clock hour (a fall-back transition), where Python calls 01:30 and its repeat (fold 1) `=` and orders 01:50 (first pass) after 01:10 (second pass). Two epochs, never behind one selector: the `...OrdinalMicroseconds` selectors (`localOrdinalMicroseconds`, `utcOrdinalMicroseconds`, `utcOrdinalMicroseconds:zone:`) count from 0001-01-01T00:00, the format's epoch; `unixMicroseconds` and `fromUnixMicroseconds:zone:` count from 1970, as `Time utcMicroseconds`; `DateTime unixEpochOrdinalMicroseconds` is the one constant between them. The constructors and the helpers they share are class-side methods (D52); an instance reaches them through its class. Constructors take Integers only (no `Float` fields, unlike `timedelta`). There is no calendar arithmetic (`DateTime + TimeSpan`) yet. A `TimeOfDay` in a `ZoneName` prints `12:00:00[Europe/Paris]`, and the instant form `2026-11-01 06:30:00Z[America/New_York]`, where Python would need the zone's rules. | ProtoBase's format 4 stores datetimes as Python's model (`@date`, `@time`, `@dt` with `["fixed", ...]` or `["instant", key]`, `@td`); its order key, hash and token never depend on a time-zone database (D58 of ProtoBase), so a key and the UTC instant are enough to store, index and compare. Shipping and updating a tz database is a separate design. Reusing the kernel names would change programs that use them. |
| D49 | **`Decimal` is a value without arithmetic: parse, print, compare, `asExactFraction`; no context, no rounding.** `lib/decimal.st` (`Import from: 'decimal'`) holds Python's decimal model (sign, coefficient, exponent; Infinity, NaN and sNaN with payloads) and its text (`str(Decimal)`), but no `+`, `*`, quantize, context, precision or traps; it is not Pharo's `ScaledDecimal` (no `1.20s2` literal, no scale). `fromString:` refuses the surrounding whitespace, underscores and non-ASCII digits Python accepts. `=` answers `false` for a signaling NaN where Python signals (`=` is what collections send); ordering any NaN, or against a non-number, signals `Error`. Arithmetic with a number is refused from either side (`1 + aDecimal` signals `Error`); comparison is symmetric through `adaptToNumber:andSend:`. `coefficient` and `exponent` answer `nil` for a special value, `payload` `nil` for a non-NaN. `asExactFraction` builds the exact value, so its cost grows with the exponent without bound (`1E+999999999999` would exhaust memory; `=`, the orderings and `hash` are not affected). `hash` is Python's (modulo 2^61 - 1, shared with `Integer`, `Fraction` and `Float`, 0.10.0): its cost grows with the length of the exponent only, and a signaling NaN cannot be hashed (`Error`, as Python's `TypeError`). | ProtoBase's format 4 needs a decimal that survives a round trip exactly (`@dec`, the format spec's "Decimal text"), not decimal arithmetic. Arithmetic with a context is a separate, larger design; a value with exact comparison is enough to store, index and compare. |
| D48 | **Deadlines are protoST's own.** `TimeoutError`, `Future after:`, `within:` and `waitWithin:` have no Pharo meaning to keep. `ms` must be a non-negative `SmallInteger` (no `Float`, no `Duration`). `within:` does not cancel the receiver. Timers still pending at exit are dropped: their futures never settle and no callback runs. A deadline fires only when a worker is free to run its settle (one blocked in I/O or `sleep:` does not count). `waitWithin:` at the top of an actor method suspends the actor; nested in a block it blocks the worker, which helps other actors meanwhile (D37), and that includes every `waitWithin:` whose `TimeoutError` is caught with `on:do:` (`[f waitWithin: 50] on: TimeoutError do: [...]`), which blocks its worker for up to the deadline. Each `within:` adds a pair of callbacks to its receiver until the receiver settles, so repeated `within:` on one long-lived Future that never settles accumulates them. An actor error that reaches the receiver after the deadline is reported as unhandled unless something else observes the receiver. A wait with no current actor on a pool worker (inside a `thenDo:` callback) blocks that worker the same way. | The timer thread never runs Smalltalk code, so a slow callback delays no other deadline; a Future that cannot be cancelled keeps its meaning for the other waiters. |
| D47 | **MessagePack: protoST's classes, with fixed choices.** `MessagePackMap`, `MessagePackExt`, `decodeOrdered:`, `decodeOrdered:strictKeys:` (an addition to the spec's list) and `decodeFirst:` are protoST names (Pharo has no MessagePack in the image). A `Symbol` encodes as `str` and decodes as `String` (D35: `#foo = 'foo'` is true here, false in Pharo). The encoding order of a `Dictionary` is unspecified (protoCore's attribute order is not API), so its bytes can differ between runs; `MessagePackMap` gives exact bytes. Ext type -1 (the timestamp) decodes to a plain `MessagePackExt`, where msgpack-python returns a `datetime`. An Integer outside -2^63 .. 2^64 - 1 signals `Error` (it never wraps or becomes a Float); a structure nested deeper than 1024 levels (msgpack-python 1.2's unpacker limit, the record depth ProtoBase format 4 requires since v2.0.0rc2; 512 up to 0.9.0) signals `MessagePackDepthExceeded` (an `Error`) on encode and decode, and one containing itself signals `Error` on encode; `Character`, `Set`, `Bag`, `Association`, `Fraction` and other classes are not encodable. Map keys must be `str` or `bin` unless `strictKeys: false`. | The bytes follow msgpack-python as ProtoBase uses it (`use_bin_type=True`, `raw=False`), so the two read each other's files. A deterministic `Dictionary` order would constrain protoCore for one codec. |
| D46 | **`BinaryFile` has no position and no stream protocol.** It is a new class, not Pharo's `File` / `BinaryFileStream`. Every read and write names its offset (from 0); `append:` answers the offset where the bytes start. `readAt:size:`, `writeAt:bytes:`, `truncateTo:`, `dataSync`, `tryLock`, `lock` and `unlock` are protoST names with no Pharo meaning to keep. The options are an Array of Symbols (`#(#read #write #create)`), not option objects. Writes take a `ByteArray` only. `writeAt:bytes:`, `truncateTo:`, `sync`, `dataSync`, `lock`, `unlock` and `close` answer the receiver. An unclosed `BinaryFile` is never closed by the collector (Pharo's file streams are finalised): it stays open, with its lock, until `close` or the end of the program; use after `close` signals `Error`, a second `close` does nothing. `FileSystem replace:with:` and `syncDirectory:` are class-side (Pharo's `FileSystem` is an instance, `FileSystem disk`). One appender at a time per file: the end guard (protoIO's `file::EndGuard`) refuses an `append:` while an `append:`, a `truncateTo:` or an extending `writeAt:bytes:` runs, a `writeAt:bytes:` while a `truncateTo:` runs (or, when it extends the file, an `append:`), and a `truncateTo:` while any of them runs, with `Error` instead of corrupting offsets or bytes (`KNOWN_ISSUES.md` K8 for what cannot be detected). `append:` on a file that is not a regular file signals `FileSystemError`. | A hidden cursor is shared state, and a file shared by several actors must not have one. Closing by finalisation would release a lock at a time the program cannot predict. |
| D45 | **Binary input and output answer `ByteArray`.** `binaryContents`, `IOStream >> nextBytes:` and UDP `receiveBytesTimeout:` answered an `Array` of Integers up to 0.8.1. An `Array` of Integers 0-255 was still accepted as an *argument* (`binaryContents:`, `nextPutBytes:`, UDP `send:`) in 0.9.0, with one line on stderr per process; since 0.10.0 every write that takes bytes or a String refuses it (`contents:`, `appendContents:`, `binaryContents:`, `IOStream >> nextPutAll:` and `nextPutBytes:`, sockets included, and UDP `send:`) with an `Error` that names the selector sent and `ByteArray withAll:` (ruling R11). | D44 | **Digests and base64: one-shot, strict, protoST names.** `crc32`, `crc32Continuing:`, `blake2b:`, `blake2b:key:`, `sha256`, `HMAC sha256Key:message:`, `CRC32 combine:with:length:`, `base64Encoded`, `base64Decoded` follow the vocabulary of Python's `hashlib` and `zlib` (Pharo has `Base64MimeConverter` and no such selectors on `ByteArray`).
