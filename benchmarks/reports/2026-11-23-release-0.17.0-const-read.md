# protoST 0.17.0 candidate: the §14.1 constant-read gate and the plain path

Date: 2026-11-23. Candidate: `feat/explicit-state-0170` at 039849a (built
from the committed tree; `--version` still prints 0.16.1, because the bump is
Task 13). Reference: protoST 0.16.1 (d657df5). Both Release builds, GCC
15.2.0, linked against the same protoCore 3.6.1 (00a90df). Raw data:
`data/2026-11-23-0170/`.

**Verdict: the gate FAILS.** `attr_lookup` is 6.1 % slower on the candidate,
against a 1 % bound. Under spec §14.1 the release is blocked until the
maintainer has the explanation and accepts the figures. The const_read bound
holds.

## Method

- **The gate script:** `benchmarks/const_read_gate.py`, with `--rounds 3`.
- **Per measurement:**
  - The binary and `libprotoCore.so*` are copied into a directory that never existed before (`$S/gate-runs/<n>`).
  - `ldd` must resolve the copied `libprotoCore.so.3.6.1`. It did for every run.
  - The standard library is the build's own, through `PROTOST_LIB`.
  - The figure is `perf stat -r 3 -x, -e cycles`: perf's mean of three runs.
  - Every run printed its `VERIFIED` line, or its `instances ok` / `vm_ops ok` line.
- **Rounds:** each round copies afresh and alternates the build order. The figures below are the means of the three rounds.
- **Process check:** no compiler, `ctest`, `ninja` or `proto*` process ran at any measurement, as `competitors_running` confirmed before each one.
- **The machine was not idle.** The 1-minute load was 4.4 to 7.6 on 12 cores, from desktop applications (an editor and a browser) that the competitor check does not cover.
  - Cycles count only the measured process, but cache and memory contention still reach them.
  - The round-to-round spread is listed with every figure, so the noise can be judged.

## Why plain reads are slower: `ivSymbol` is no longer inlined into runLoop

The handlers were extracted from `runLoop` through the dispatch table: the `kLabels` RELATIVE relocations, from each label to the next one. The script is `data/2026-11-23-0170/objdump/handlers.py`. The handlers were then normalised and compared; the `.s` and `.diff` files are in the same directory.

| Handler | 0.16.1 vs 0.17.0 |
|---|---|
| `PUSH_INSTVAR` | **Different code.** In 0.16.1, `BytecodeModule::ivSymbol` is inlined: a test of the cache pointer and a bounds compare, then a jump to the cached-symbol load, with `ivSymbolSlow` called only on a miss. In 0.17.0 the handler makes an out-of-line **`call BytecodeModule::ivSymbol`** on every read. The rest of the handler is the same instruction sequence. |
| `PUSH_OWN_INSTVAR` | **Different code,** in the same way: an out-of-line `call ivSymbol`. |
| `STORE_INSTVAR` | Equivalent. The differences are register allocation, frame offsets (the runLoop frame grew by 0x100 bytes, so `[rbp-0x4b8]` became `[rbp-0x5b8]`) and nop padding. |
| `storeInstVar` (the helper STORE_INSTVAR calls) | Equivalent. Register allocation differs, and one push/pop of r13 replaces a stack spill. |
| `IVAR_GROUP` | Equivalent: register allocation and padding. |
| `IVAR_GROUP_END` | Equivalent in structure: the same branches, one call to `storeInstVar` and the same dispatch tail. Its source changed in Task 8 (the shared tail), and register allocation differs, with one more spill slot. |

`ivSymbol` is still an inline function in `BytecodeModule.h`, and its source did not change since 0.16.1. In 0.16.1 the binary has no out-of-line copy of it, and runLoop calls it 0 times. In 0.17.0 there is a weak out-of-line copy, and runLoop calls it from 5 sites.

The likely cause is GCC's inliner budget for runLoop. That budget is a function-growth limit, and the new handlers (`PUSH_CONST_INSTVAR`, `STORE_CONST_INSTVAR`, `STORE_ONCE_INSTVAR`) each add an `ivSymbol` call site and code to an already huge function. Once over the limit, GCC stops inlining `ivSymbol` into every call site, the plain-read handlers included. This is a compiler-heuristic effect, not a change to the plain-read source.

A `perf record` of one attr_lookup_10x run per build (attribution only, not a figure) agrees. It puts 23.5 M cycles in `BytecodeModule::ivSymbol` on 0.17.0 and none on 0.16.1. Files: `perf-old-top.txt` and `perf-new-top.txt`.

Nothing was changed to fix it, because the gate rules allow only the `PUSH_OWN_CONST_INSTVAR` remedy (spec §16), and that remedy is for const_read.

A possible remedy for the maintainer to decide is to mark `BytecodeModule::ivSymbol` (and `constSym`) `__attribute__((always_inline))`, or to raise the inliner limits for `ExecutionEngine.cpp`, which `CMakeLists.txt` already does for `max-goto-duplication-insns`. It has not been built or measured.

| Program | 0.16.1 | 0.17.0 | Ratio | Per round |
|---|---:|---:|---:|---|
| `micro/instances.st` | 10,991,659,518 | 11,682,929,187 | 1.063 | 1.127, 1.052, 1.009 |
| `micro/vm_ops.st` | 4,138,531,967 | 4,122,349,633 | 0.996 | 1.014, 0.970, 1.007 |
| `micro/point_new.st` (300000 × `Point x:y:`) | 2,319,086,341 | 2,625,251,882 | **1.132** | 1.059, 1.166, 1.174 |
| `micro/fraction_new.st` (300000 × `Fraction numerator:denominator:`) | 3,219,498,964 | 3,441,156,712 | **1.069** | 1.117, 1.043, 1.047 |

- **`instances.st`** is 6.3 % slower on the mean, but its rounds range from +0.9 % to +12.7 %. On this machine that is at or near the noise.
- **The hot constructors** are slower beyond noise in every round:
  - Point: about +1,000 cycles per construction.
  - Fraction: about +740 cycles per construction.
- **Attribution of the constructor cost.** A `perf record` of one point_new run per build shows `ProtoObject::getAttribute` rising from 180 M to 293 M cycles, `getOwnAttributeDirect` from 101 M to 136 M, and runLoop from 289 M to 341 M. That fits the cost of the `__checkConstructed:selector:` send plus its read of `__has_constants__` through the class chain. For a class without constants, that read misses on every level of the chain.

### C20: `new`'s `__hasConstants` send against the one-primitive form

The alternative kernel replaces the two sends in `Object class >> new` (`__hasConstants ifTrue: [__checkConstantsOf:after:]`) with one `^ self __checkConstructed: instance selector: #new`. Its behaviour is the same. The diff is `c20-alternative.diff`, and it was measured through `PROTOST_LIB` on the same 0.17.0 binary.

| `instances.st` | Cycles (3 rounds) | Per round |
|---|---:|---|
| 0.17.0 kernel (two sends) | 11,311,592,306 | 11.13 G, 11.10 G, 11.71 G |
| alternative (one primitive) | 11,651,799,235 | 11.36 G, 11.89 G, 11.71 G |

The alternative is not faster: it is +3.0 %, within the noise. It is not committed.
