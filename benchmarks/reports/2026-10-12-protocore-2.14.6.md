# protoST on protoCore 2.14.6 — 2026-10-12

**Synthetic benchmarks on one notebook-class machine** (DEV12: AMD Ryzen 5
5500U, 6 cores / 12 threads, 62 GB, Ubuntu 26.04, kernel 7.0.0, glibc 2.43,
a desktop session with a browser open). Nothing here was measured on a
server. Raw data and scripts: [`data/2026-10-12-2146/`](data/2026-10-12-2146/).

## Question

protoCore 2.14.6 (released 2026-10-12) changes two things protoST's
pre-talk audit reported (protoCore `docs/reports/2026-10-12-mark-stack-int-compare.md`):

- the collector's mark work list is a fixed 8 MiB stack (mark-on-push,
  overflow rescan) instead of a vector that doubled up to 512 MB;
- comparing, dividing and taking the modulo of two SmallIntegers no longer
  allocates temporaries.

What does that change for protoST, on the whole benchmark suite, on the
talk's demo 2 and on K5, and which figures quoted in the README and the FAST
talk must change?

## Builds

One binary, two libraries. Both sides run the **same `/usr/bin/protost`**,
the protoST 0.6.4 release package (built in an Ubuntu 24.04 container with
GCC 13). `LD_LIBRARY_PATH` selects `libprotoCore.so.3` from the GitHub
release `.deb` of protoCore 2.14.5 or 2.14.6, extracted unchanged (SHA-256
in `results/sha256.txt`; the 2.14.6 library is byte-identical to the one
staged by the protoCore agent). Before **every** run the harness ran `ldd`
under the run's environment and refused the run if it resolved another
library; each sample records the resolved path. protoST 0.6.5 changes no
code against 0.6.4, so these are 0.6.5's figures as well.

## Method

- **Wall time, CPU time, peak RSS**:
  [`benchmarks/compare_builds.py`](../compare_builds.py), with the new
  `--libdir` option, every library listed twice (A/A pairs: `2145a`/`2145b`,
  `2146a`/`2146b`), one discarded round and 7 measured rounds, the order
  rotating each round. The tables give the median of the 14 runs of each
  version (both copies pooled) and the difference between the two copies'
  medians of 7 as the noise floor. CPU time is `ru_utime + ru_stime` of the
  child (all threads); peak RSS its `ru_maxrss`.
- **Cycles and instructions**: `perf stat -r 5 -e cycles,instructions`, all
  threads (`perfstat.py`).
- **Demo 2**: `02-actors-parallelism.st` exactly as the talk runs it,
  15 alternating rounds per series (`demo2.py`); each run checked against
  `expected/02-actors-parallelism.out` (4946 primes twice, `true`).
- **K5**: `(1 to: 500000) asArray` under the fixed 640 MB limit
  (`PROTOCORE_ADAPTIVE_HEAP=0`, out of memory, exit 3 expected) and under the
  default controller (completes), 5 runs per side, peak RSS from GNU `time`
  (`k5.sh`).
- **CPython 3.14.0**: `benchmarks/run_benchmarks.py --runs 7 --warmup 1
  --skip-actors`, once per library.
- **Every run verified its computed result** (`VERIFIED <value>`, exit
  status 0; K5's expected exit status and output); none failed.
- **Quiet machine.** The session (`run_all.sh`, 18:29-18:42) started after
  90 consecutive seconds with no compiler, build tool, test runner or other
  protoCore runtime running and the one-minute load below 3 (another agent
  was measuring other runtimes on this machine during the day). The harness
  records, per run, the competing processes (none in any run) and the
  one-minute load: 2.7-8.1, the upper part caused by the session's own
  multi-worker runs (`saturation_big` with five and six workers, demo 2).

|---|---:|---:|
| start-up, protoST / CPython | 25.0 / 34.8 ms | 26.4 / 31.9 ms |
| whole-process ratio, range | 0.91× (`str_concat`) to 22.0× (`exception_latency`) | 0.92× to 21.4× |
| whole-process ratio, geometric mean | **3.28×** | **3.20×** |

The two columns are two runs of the same comparison a few seconds apart;
the protoST times differ by less than their own spread. As in the 10/11
report, the whole-process ratio is stable (3.2-3.3×) and the work ratio is
not: at these N it is the difference of two similar times, and a few
milliseconds of noise in either start-up move it (`list_append`'s CPython
work time was below its start-up's noise in the first run and has no
ratio). Quote it as a range, about 14-20×.

## Reading the numbers

1. **The benchmark suite barely moves.** Its programs compare and divide few
   integers outside the interpreter's own fast paths. Instructions fall
   1-3.5 % almost everywhere; wall time is unchanged within the A/A noise
   except `exception_latency` (-6.9 % wall, -10.4 % cycles) and
   `parallel_speedup` with the full pool (-7.7 %, against A/A differences
   of 3-4 %). Which part of 2.14.6 helps exceptions was not isolated.
2. **Demo 2 changes a lot**, because `isPrime` is integer comparison and
   modulo in a loop: the one-thread half is 45 % faster, the twelve-actor
   half 35 % faster. The printed ratio therefore falls, from 4.4× to 3.8×
   (median, series 1): a faster single thread shrinks the numerator more
   than the denominator. Both absolute times improve. The protoCore report
   measured the same direction on a busier desktop (one thread 1,313 ->
   879 ms, twelve actors 446 -> 329 ms, ratio 2.99 -> 2.66); its absolute
   values differ from these (a different session on a desktop with more
   running; the difference was not investigated), so the talk quotes this
   report's.
3. **K5 is fixed in the way that matters**: under the fixed limit the
   process now peaks at 690 MB, 50 MB above the 640 MB of cells, instead of
   1,165 MB, and reaches the out-of-memory exit in half the time.
4. **Regressions.** None beyond the noise in wall time. `fib` (+2.1 % wall,
   +3.8 % CPU, A/A up to 11 %) and `message_throughput` (+3.8 %, A/A 8-9 %)
   are within their noise; their cycles are unchanged (-0.5 %, +0.4 %).
   The multi-worker `saturation_big` ratios are 1-3 % lower on 2.14.6, also
   within the spread, and the six-worker run used 219 MB against 206 MB.
5. **Absolute figures.** This session's 2.14.5 figures are close to those of
   the 0.6.2 report of 12/10 (start-up 25 ms, `saturation_big` 1.0-2.9 s),
   which used a GCC 15 build; this one uses the GCC 13 release binary.
