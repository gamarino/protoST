# protoST on protoCore 2.14.5 — re-measurement, 2026-10-11

**Synthetic benchmarks on one notebook-class machine** (DEV12: AMD Ryzen 5
5500U, 6 cores / 12 threads, 8 MB L3, two memory channels, Linux
7.0.0-34). Nothing here was measured on a server. The raw data and the
scripts are in [`data/2026-10-11/`](data/2026-10-11/).

## Question

Between protoST 0.5.0 (2026-09-29) and `main` at `4876884` protoCore went
from 2.6.2 to 2.14.5: allocation pacing, early wake, a multi-cursor sweep with
helper threads, an optional adaptive heap controller and `setAttributes`
write coalescing, which protoST uses for runs of instance-variable
assignments. protoST keeps its fixed heap limit (10M cells, 640 MB) and does
not enable the controller (`KNOWN_ISSUES.md`, K5). Did any of this change
protoST's numbers, and are the figures cited in the README and the FAST talk
still right?

## Builds

Three builds, all Release, run side by side:

| Label | protoST | protoCore | Notes |
|---|---|---|---|
| `0.5.0 / 2.6.2` | tag `v0.5.0` | 2.6.2 (tag `v2.6.2`) | the release as published; both built from source for this report |
| `2026-10-03 / 2.10.2` | `main` of 2026-10-03 (`5badd33`) | 2.10.2 | the installed 2026-10-03 packages (`/usr/bin/protost`, reports 0.5.0) |
| `main / 2.14.5` | `main` at `4876884` | 2.14.5 (tag `v2.14.5`) | linked against a private 2.14.5 prefix (checked with `ldd`) |

## Method

- [`benchmarks/compare_builds.py`](../compare_builds.py): for every workload,
  one warm-up round and three measured rounds; each round runs every build
  once, in an order that rotates from round to round. The table gives the
  median of the three. Every run is verified: the program's last line must be
  `VERIFIED <expected>` and the exit status 0, or the script fails. Peak RSS
  is the child's `ru_maxrss` from `wait4`.
- Two sessions, A (13:33) and B (13:45), each started only when no compiler,
  build tool, test runner or protoCore runtime of another agent was running
  and the one-minute load was below 5 (other agents were building and testing
  on this machine all day; the desktop keeps about 2.5 CPUs busy). No run in
  either session started while such a process was running. The load average
  during the sessions was 2.9 to 6.7, part of it from the benchmarks
  themselves (`saturation_big` with six workers).
- `benchmarks/run_benchmarks.py` (1 warm-up + 3 runs) for the CPython 3.14.0
  comparison, as in the 0.4.0 report.
- `perf stat -r 3` (task-clock, cycles, instructions) on start-up (`-e 1`),
  `fib.st` and `int_sum_loop.st`, in two rounds, the builds alternating.

### Against CPython 3.14.0 (`run_benchmarks.py`, `main / 2.14.5`)

Start-up 31.6 ms (CPython 36.0 ms). Whole-process time 1.03× (`str_concat`)
to 26.4× (`exception_latency`) CPython's, **geometric mean 3.52×**. With
each runtime's start-up subtracted, the work itself takes 4.6× (integer
loop), 16× (`attr_lookup`), 31× (`fib`) and 82× (exceptions) CPython's time,
**geometric mean 16.4×** over the five long enough to measure. The same
harness run on `0.5.0 / 2.6.2` a minute later gave 3.55× and 26.5×: the
whole-process ratio is stable, the work ratio is not. At these small N the
work is a difference of two similar numbers, so a few milliseconds of noise in
either start-up move it a lot (`int_sum_loop`: 4.6× in one run, 22.5× in the
next). Quote it as a range, about 16-27×, not as one figure.

## Reading the numbers

1. **Single-threaded speed did not change.** The interpreted code executes
   the same instructions within 1 % (start-up 3 % fewer) on all three builds,
   and the wall-time medians differ by less than the spread between the two
   sessions. protoCore's collector work does not show here, as expected: these
   programs collect little, and protoST's fixed limit is far above their live
   sets.
2. **Memory is slightly lower on `main`**: 12 MB less peak RSS on `fib`,
   `attr_lookup`, `range_iterate`, `exception_latency` and `list_append`
   (24 MB less than the 2026-10-03 build on `list_append`). `range_iterate` and `list_append` are also 9-16 % faster in
   both sessions. Which protoCore change gives this was not isolated.
3. **A small regression on allocating actor workloads, cause not isolated.**
   With one worker, `parallel_speedup` (+5-6 %), `cooperative_yield` (+4 %)
   and `saturation_big` (+5 %) are slower on `main / 2.14.5` than on both
   older builds, in both sessions. A diagnostic session
   ([`data/2026-10-11/compare-diagnostic.json`](data/2026-10-11/compare-diagnostic.json))
   ran `main` with pacing off (`PROTOCORE_GC_PACING=0`), with one sweep cursor
   (`PROTOCORE_GC_SWEEP_CURSORS=1`) and without instance-variable write groups
   (`PROTOST_IVAR_GROUPS=off`); none of them recovered the gap consistently
   (`saturation_big` with one worker: 3666 ms default, 4046 without pacing,
   3796 with one cursor, 3672 without write groups, against 3544 for 0.5.0),
   and that session ran at a higher load than A and B. The gap is small
   against the session-to-session spread, so it is reported here, not
   explained.
4. **Parallel scaling is unchanged** within the noise: twelve CPU-bound
   actors run 2.5-2.8× faster on the pool than on one worker, and
   `saturation_big` tops out at about 2× (four workers) on every build. The
   0.4.0 report's 2.1× for twelve actors came from a faster one-worker run on
   that day (732 ms, 981-1038 ms today); the same 0.5.0 binary gives 2.7×
   today, so the difference is the machine's state, not the code.
5. **Absolute times are about 15 % slower than the 0.4.0 report's**
   (`fib` 380 ms then, 441-448 ms today for every build, including 0.5.0).
   The machine was busier today (other agents, desktop), so compare builds
   within this report, not across reports.
