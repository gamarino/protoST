# Before the talk: transient pins, demo 2 in a container, K5's resident memory — 2026-10-12

Three findings of the pre-talk audit of 0.6.2, measured on DEV12 (AMD Ryzen 5
5500U, 6 cores / 12 threads, 62 GB, Ubuntu 26.04, kernel 7.0.0, glibc 2.43,
GCC 15.2; CPU governor `powersave`), with a desktop session open (browser),
1-minute load 3-5. Raw data: [`data/2026-10-12-063/`](data/2026-10-12-063/).

## 1. The threaded dispatch did not release transient pins (fixed in 0.6.3)

**Defect.** GCC 15 printed 1081 warnings on `src/runtime/ExecutionEngine.cpp`,
"jump to label ... does not destroy 'pinX'": 23 dispatch points (every SEND,
PUSH_BLOCK, the global and class-variable accesses) times the 47 labels a
computed goto may reach. The warning is literal: a computed goto runs no
destructor (checked with a five-line program), so `~TransientPin` never ran at
those points and the thread's scratch cursor never came back down. Read with
gdb at `_exit`, the main thread's `g_scratchCursor` was 255 of 256 after a
script of one expression (0 for `--version`): the kernel load alone used up
the scratch region. From then on a Release build's `TransientPin` pinned
nothing, because the overflow check is an `assert`. Every value the runtime
pins across an allocation was therefore unrooted on the GCC builds (Linux
packages and Linux CI) since the threaded dispatch existed; Clang (macOS) and
MSVC (Windows) use the switch dispatch, whose `goto` does run destructors.
No crash has been traced to it; it is the kind of defect that shows as a rare
use-after-free.

**Fix.** The 23 points leave through `DISPATCH_SCOPED()`, an ordinary `goto`
to the dispatch loop's head, which destroys the locals of the scopes it
leaves; the loop head then decodes the next instruction as the switch build
does. Every remaining `DISPATCH_DIRECT` is in a scope without such a local,
and GCC checks it: the build has no warnings, so a new one would show.
Test: `TransientPin: every instruction releases its pins`
(`tests/unit/test_heap_policy.cpp`); before the fix it read 255 against 0.

**Cost** (`compare-062-vs-pinfix*.json`, `perfstat.txt`; 0.6.2 against the
fix, same compiler and protoCore 2.14.5 library, A/A pairs, medians of 7 and
of 15 runs; `perf stat -r 5`, all threads):

| Workload | 0.6.2 | fix | Δ wall | Δ cycles | Δ instructions |
|---|---:|---:|---:|---:|---:|
| startup | 24.6 ms | 24.4 ms | -1.0 % | | |
| int_sum_loop | 46.8 ms | 47.2 ms | +0.8 % | 0.0 % | +0.3 % |
| fib | 373 ms | 382 ms | +2.2 % | -0.8 % | -0.2 % |
| attr_lookup | 175 ms | 182 ms | +4.0 % (+7.1 % in the 15-run rerun) | -1.8 % | +1.4 % |
| exception_latency | 948 ms | 1,073 ms | **+13.2 %** | **+6.2 %** | **+29.5 %** |
| parallel_speedup pool | 243 ms | 286 ms | +17.8 % (-2.8 % in the 15-run rerun) | | |
| parallel_speedup w=1 | 691 ms | 699 ms | +1.2 % | | |
| message_throughput | 76.4 ms | 77.3 ms | +1.2 % | | |
| saturation_big w=1 | 2,836 ms | 2,802 ms | -1.2 % | | |

The machine was noisy (A/A spreads up to 23 % on the pool row); the cycle
counts are the steadier measure. Only `exception_latency` is clearly slower.
The same number of exceptions is thrown (1,000 for 2,000 iterations in both
builds, counted with gdb) and the C++ personality routine is called the same
number of times (19 per throw), but each call costs more: the extra
instructions are in `__gxx_personality_v0` and its helpers in libstdc++ (13 %
of instructions before, 34 % after). The routine searches the call-site table
of `runLoop`, a very large function, linearly, and the change of code layout
moved the call sites an exception crosses further into that table; the
table itself did not grow. Programs that do not throw are unchanged within
the noise.

## 2. Demo 2 inside an Ubuntu 24.04 container

The audit saw demo 2's speedup at a median of about 2.5× in an Ubuntu 24.04
container on this machine, against 4.45× in the 0.6.2 report. Alternating
runs (`demo2-container/r2.txt`, `r3.txt`, `r4.txt`; 10-12 rounds each):

| Series | Configuration | one thread | 12 actors | speedup, median (range) |
|---|---|---:|---:|---|
| `r3` | GCC 13 release binary, in the container (Ubuntu 24.04 userland) | 1,302 ms | 322 ms | 4.17× (2.93-4.57) |
| `r3` | GCC 13 release binary, on the host with the container's loader and libraries (glibc 2.39) | 1,266 ms | 326 ms | 3.88× (2.37-4.41) |
| `r3` | GCC 13 release binary, host libraries (glibc 2.43) | 1,443 ms | 329 ms | 4.38× (2.75-5.05) |
| `r3` | GCC 15 local build, container's libraries | 1,276 ms | 323 ms | 3.98× (1.91-4.50) |
| `r3` | GCC 15 local build, host libraries | 1,388 ms | 377 ms | 3.76× (2.60-4.70) |
| `r4` | GCC 13 release binary, host libraries | 1,385 ms | 308 ms | 4.53× (3.17-5.03) |
| `r4` | GCC 13 release binary, host glibc with the container's libstdc++ | 1,377 ms | 308 ms | 4.49× (2.90-5.03) |
| `r4` | GCC 13 release binary, container's libraries | 1,242 ms | 300 ms | 4.20× (2.36-4.83) |

Each series alternates its configurations round by round; compare rows
within a series.

- **The container is not slower.** The twelve actors take the same time
  everywhere. What changes is the one-thread half: about 10 % *faster* with
  Ubuntu 24.04's glibc 2.39 than with the host's glibc 2.43, in or out of a
  container, so the ratio drops.
- **glibc's malloc is the difference, not the compiler or libstdc++.**
  Swapping only libstdc++ changes nothing; swapping glibc does. The profile
  of the one-thread part (`perf-d2h.txt`, `perf-d2c.txt`) puts libc at 18 %
  of the samples under glibc 2.43 against 12 % under 2.39, all in
  `malloc`/`free`. The allocations come from protoCore's
  `proto::toTempBignum`, which builds a temporary through `operator new` for
  the integer comparisons inside `isPrime`. That is a protoCore matter
  (reported, not changed here).
- The container had no CPU quota (`cpu.max` = `max`) and saw all 12 CPUs;
  the governor is the host's.
- Every configuration dropped to 2-3× in the rounds that ran while the
  machine was busy, so the audit's 2.5× median most likely also includes the
  load of that moment; that part is not proven.

Nothing to fix in protoST. The talk materials now say the figure depends on
the machine (typically 3-5×) and demo 2 prints its own ratio.

## 3. K5: 1.19 GB resident under the "640 MB" limit

With `PROTOCORE_ADAPTIVE_HEAP=0` (0.6.1's fixed limit of 10M cells),
`(1 to: 500000) asArray` stops with the out-of-memory message after a peak
RSS of 1.19 GB. protoCore caps the cells it takes from the system
(`heapSize` never crosses `maxHeapSize`), so the excess is memory outside
the cell heap. At the out-of-memory point glibc reported 743 MB in use and a
peak of 1.45 GB in mapped regions. Breaking on `mmap` above 20 MB
(`k5-mmap-backtraces.txt`) shows where: besides the cell blocks, the
collector thread's mark phase (`gcThreadLoop`, the callback that
`processReferences` calls for each reference) grows a `std::vector` by
doubling, 32, 64, 128, 256 and 512 MB, and each doubling holds the old
buffer while it copies. That work list is not counted against the cell
limit. The fixed limit bounds the cells, not the process; this is protoCore
behaviour, reported, not changed here.
